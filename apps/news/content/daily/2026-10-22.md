## 오늘 하나만 본다면

### 코드를 이해하지 못할 때 에이전트로 디버깅하기

`Martin Fowler` [원문](https://martinfowler.com/fragments/2026-10-21.html)

에이전트에게 버그를 맡길 때 코드를 먼저 읽게 하는 것은 안티패턴이고, 코드 읽기는 조사의 맨 마지막 수단이어야 합니다.

- 핵심은 Cindy Sridharan의 장문 글 "How to effectively debug when you no longer understand the code"를 Fowler가 요약한 대목입니다. 출발점은 "에이전트는 사람이 아니다"라는 관찰입니다. 에이전트에게 사람의 문제 풀이 방식을 흉내 내게 하지 말고 에이전트의 강점을 쓰라는 것입니다.
- 버그 조사는 코드 읽기로 시작하지 않습니다. 코드를 읽어 가설부터 세우는 일은 조사의 맨 마지막 수단이어야 합니다. 먼저 시스템 동작에 대한 원자료(사실 계층)를 모두 모으고, 그다음 그 사실을 전부 만족하는 가설(가설 계층)을 찾습니다.
- 절차는 세 단계입니다. 사실 중 버그와 관련 있는 신호를 가려내고(이때 버그가 나지 않는 동작이라는 고품질 대조군이 필요합니다), 신호와 가장 잘 맞는 가설을 표로 비교하고, 남은 가설을 모든 사실에 제약 조건으로 대어 검증합니다.
- 사람과 에이전트는 데이터 취향이 반대입니다. 사람은 적은 데이터를 원해서 집계와 시각화를 만들었지만, 에이전트에게 집계는 신호의 가치를 없애는 경우가 많고 로그는 많을수록 좋습니다. 인용된 저자의 경험으로는 세 버그 모두 에이전트가 혼자 원인에 닿을 능력이 있었지만 대조군을 세우는 일조차 사람이 시켜야 했습니다.
- 같은 글의 앞부분에서 Fowler는 Gergely Orosz의 "AI 흔적이 보이면 전부 AI라고 간주한다"는 입장에 동의하면서도, 번역에 AI를 쓰는 비영어권 저자에게 불공정할 수 있다는 단서를 답니다.

결론은 에이전트 중심 세계에서 잘하는 엔지니어가 코드를 이해하는 사람이 아니라 검증 루프를 설계하는 사람이라는 것입니다. AI 시대의 리뷰와 검증 체계를 고민한다면 "대조군을 세우고 검증되지 않은 가설을 기각하는 것"이 사람의 일이라는 정의가 구체적인 출발점이 됩니다. 장애 조사에 에이전트를 붙여 본 적이 있다면 대시보드부터 보여 준 것이 왜 안 통했는지도 설명됩니다.

### 웹 컴포넌트는 아무도 쓰지 않는 시대에 미래가 있나

`Nolan Lawson` [원문](https://nolanlawson.com/2026/10/19/do-web-components-have-a-future-if-nobody-is-writing-them/)

웹 컴포넌트를 수년간 만든 저자가 직접, Google의 에이전트용 웹 가이드가 첫 6개월간 웹 컴포넌트를 거의 언급하지 않았다는 점을 근거로 그 존재 이유가 약해졌다고 씁니다.

- 웹 컴포넌트는 사람이 HTML을 손으로 치고 코드가 귀하니 재사용이 경제적 필수이던 세계를 전제로 설계됐습니다. 에이전트가 UI를 처음부터 생성하는 지금은 "공통 표준으로 만들면 쉽게 재사용된다"는 핵심 가치가 크게 약해졌다고 씁니다. 저자는 웹 컴포넌트 기반 프레임워크 LWC를 수년간 만든 사람이라 이 결론이 쓰기 고통스러웠다고 밝힙니다.
- 근거로 Google의 Modern Web Guidance를 듭니다. 에이전트가 CSS scroll snap, scroll-driven animations 같은 최신 브라우저 기능을 쓰도록 유도하는 스킬 모음인데, 첫 6개월간 웹 컴포넌트 언급이 거의 없었고 3주 전 커밋 하나로 비로소 들어왔습니다. 내용도 "커스텀 엘리먼트가 정말 필요한지 먼저 판단하라"는 식이라 새 제품을 만드는 에이전트가 웹 컴포넌트를 고를 가능성은 낮다고 봅니다. 쉐도우 DOM의 CSS 성능 이점도 Svelte, Vue, Tailwind 같은 컴파일 타임 스코핑으로 똑같이 얻는다고 직접 벤치마크했다고 말합니다.
- 영향은 웹 컴포넌트에서 끝나지 않습니다. "에이전트에게 더 낫다"는 분위기만으로 프레임워크를 통째로 갈아엎는 팀이 늘고 있고, 프레임워크 층을 일회용으로 보면 그 아래 층에 가치를 두기는 더 어렵습니다. shadcn처럼 보일러플레이트를 직접 소유하는 방식은 LLM 덕에 단점이 장점으로 바뀝니다. 다만 저자는 이런 재작성이 "토큰이 덜 든다", "사용자 경험이 빠르다" 같은 근거 위에서 이뤄져야 한다고 덧붙입니다.
- 구해낼 여지는 두 가지입니다. 에이전트 여럿이 UI의 다른 부분을 맡을 때 CSS, 이벤트, 전역을 격리하는 마이크로 프런트엔드 용도, 그리고 스탠드얼론 `<emoji-picker>` 같은 재사용은 여전히 의미 있다는 논리입니다. 하지만 격리는 iframe이 더 강하고, React가 이미 에이전트의 재사용 층이라는 반론에는 React가 마지막 프레임워크일 리 없다고 답합니다.

결론은 지지자가 표준, 프레임워크, 브라우저 쪽에서 두 배로 노력해야 한다는 것입니다. 서버 사이드 렌더링, 스타일시트 공유, 접근성이 여전히 미해결이고 이는 AI 코딩과 무관하게 사용자 경험에 직접 닿는 결함이라는 지적이 실무에 더 가깝습니다. 가장 서늘한 논거는 어떤 프레임워크든 결국 AGENTS.md의 각주 정도로 밀려날 수 있다는 것입니다.
